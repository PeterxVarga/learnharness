# R16.4 — Namespaced Add-on Migration / Upstream Reality Gate

## Problem falsified

R16.3 exported R15 additions into a portable pack, but assembled them at their **old repository paths** (`components/gusek-*.tsx`, `src/features/gusek/`, `pilots/operations-research/`). As upstream evolves, this makes namespace collisions likely and contradicts the user's upstream-first objective. A test reproduced that upstream taking ownership of `components/gusek-workbench.tsx` blocked R16.3 even though there is no fundamental application/API incompatibility.

## This batch's outcome

R16.4 relocates selected R15 source under `src/tredven/addons/<original R15 path>` **inside the disposable assembled application only**. Relative import structure remains intact. Static `@/` imports pointing to a selected R15-added module are rewritten to the new private namespace; unknown imports are not silently shimmed. The one approved Workbench type-only compatibility seam is retained and points to `@/src/tredven/gusek/attempt-receipt-r15`.

Exactly these app-router paths remain outside Tredven-owned source paths:

- `app/pilot/gusek/page.tsx` — route page whose import points at namespaced UI;
- `app/api/pilot/gusek/route.ts` — thin bridge with explicit literal Next.js segment configuration and GET/POST re-exports;
- `app/api/pilot/gusek/native/route.ts` — **optional** bridge to the existing disabled-by-default R15 native diagnostics, never a grading endpoint.

All other selected files live under `src/tredven/addons/`, except the private compatibility type under `src/tredven/gusek/`. The `core` profile's standalone UI is now also namespaced.

R16.4 **does not** rewrite original upstream files or touch user chats/knowledge graph, nor does it create a runtime plugin registry, new grader, solver, database, or parallel teacher agent. An upstream-added `components/gusek-workbench.tsx` no longer collides; if upstream takes a necessary app route, assembly blocks.

## New verification contract

`verify-assembly` recomputes the expected source closure from the frozen pack, selected profile and optional native feature. It independently checks:

1. The `selected_module_closure` matches the frozen package.
2. The assembled add-on file set matches precisely the renamed source paths, allowed overlay paths and necessary thin route shims.
3. The API bridges equal the exact deterministic generator output, *not merely their self-reported receipt hash*.
4. The namespaced source content is reproducible byte-for-byte from the frozen R15 source plus the two documented transformations.
5. The same requirement applies to the private UI overlays.

This is an **accidental-drift safeguard**, not an independently signed provenance claim. A fully malicious operator controlling the scripts and trust roots is not covered.

## Commands / existing workflow

Use the R16.4 tool bundle instead of R16.3. Previously frozen R16.3 source packs can be reused (provided their original source and overlay hashes verify); **assemblies from R16.3 must be regenerated under R16.4** before the first upstream refresh. `compare-assemblies` intentionally rejects changes to the namespace scheme.

```bash
BUNDLE="$HOME/Downloads/learnharness-r16-upstream-first-r164"
FORK="$HOME/path/to/pinned-fork"
UPSTREAM="$HOME/path/to/upstream"
PACK="$HOME/Downloads/learnharness-r15-addon-pack"
OUT="$HOME/Downloads/learnharness-r164-clean"

# Exactly once if the frozen pack does not already exist:
python3 "$BUNDLE/r16.py" freeze-pack --r15 "$FORK" --out "$PACK"
python3 "$BUNDLE/r16.py" verify-pack --path "$PACK"

# Source-only clean 0.4.1 assembly (upstream commit must already be locally present):
python3 "$BUNDLE/r16.py" assemble-pack --upstream "$UPSTREAM" \
  --upstream-ref e69e85269c064c6c9c49a8b06ae78c06e79c4a63 \
  --addon-pack "$PACK" --profile workbench --out "$OUT"
python3 "$BUNDLE/r16.py" verify-assembly --path "$OUT"

# ONE final owner-approved application qualification:
bash "$BUNDLE/qualify-r16.sh" "$OUT"
```

`--native-route` is an optional installation of source only and must be given during assembly if desired; qualification continues to set `LH_GLPK_ENABLE_LOCAL=0` and strip GLPK secrets. Native Podman/GLPK execution and browser visual checks require separate, expressly authorized execution on the real Fedora host.

A new upstream candidate can be compared with `plan-update` after a baseline R16.4 assembly is qualified; it reuses the same frozen pack and rejects profile, native-route and pack-identity drift.
