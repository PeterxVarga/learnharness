# LearnHarness R16.3 — portable addon source + upstream update planning

## Why this batch exists

R16.2 still required a locally available R15 Git history for every assembly. It also lacked an explicit portable pack identity, making it hard to prove that a future upstream refresh used **the same** GUSEK/R15 add-on sources. This chunk fixes that lifecycle problem, rather than introducing a parallel plugin manager.

## Core model

1. **Once**: `freeze-pack` exports *all new (A) files* from the pinned R15 commit relative to common base, plus the exact R16 integration overlays. The R15 `M/D` changes remain a quarantine-only diff. Outputs `pack-lock.json` with exact file hashes and source refs, and validates three dependency graphs (`core`, `workbench`, `workbench+native-route`).
2. **Repeatedly**: `assemble-pack` reads a previously frozen pack plus an arbitrary locally checked-out upstream commit. It creates a disposable directory with a pristine upstream Git archive plus selected add-on files. It never changes either checkout or pack; it refuses name/case collisions, missing dependencies and an unexpected R15 compatibility-seam shape.
3. **Next upstream**: `plan-update` uses the SAME frozen add-on pack to construct a candidate and compare its upstream file inventory with a previous assembled build. Report: added/modified/deleted file names, risk classification and NO_GO until explicit review. It will not silently swap profile, GLPK endpoint mode or pack identity.
4. **Eventually once**: the existing `qualify-r16.sh` runs the real Node/TypeScript/Next/unit/HTTP checks after operator approval, and now repeats the full source hash proof **after** the build and runtime smoke. Generated `node_modules/`, `.next/`, `next-env.d.ts` and `tsconfig.tsbuildinfo` are excluded only from the *post-build path-set* check (never from a tracked file's hashes); all other unexpected source additions still fail.

The hard-coded source pins in `r16.py` ensure that this R16.3 only produces a package from the exact, previously Fedora-qualified R15 source. The pack lock is a local integrity receipt, **not** signed provenance, an attestation or a proof against an attacker who can rewrite both pack and lock. All integration output is `ASSEMBLED_UNQUALIFIED`, not released.

## Recommended one-time packaging (offline, no Node/npm needed)

```bash
BUNDLE="$HOME/Downloads/learnharness-r16-upstream-first-r163"
FORK="$HOME/path/to/learnharness-fork-with-R15-commit"
PACK="$HOME/Downloads/learnharness-r15-portable-addon-pack"

python3 "$BUNDLE/r16.py" freeze-pack --r15 "$FORK" --out "$PACK"
python3 "$BUNDLE/r16.py" verify-pack --path "$PACK"
```

The fork checkout can then be archived separately. The pack is a content-locked *source directory* (not a compiled artifact). Keep this R16.3 tool bundle together with it; do not discard original Fedora R15 evidence.

## Build the current upstream without the old R15 checkout

```bash
UPSTREAM="$HOME/path/to/clean-learnharness-upstream"
OUT="$HOME/Downloads/learnharness-r163-initial"
# Upstream repository must already hold this immutable commit locally.
python3 "$BUNDLE/r16.py" assemble-pack \
  --upstream "$UPSTREAM" --upstream-ref e69e85269c064c6c9c49a8b06ae78c06e79c4a63 \
  --addon-pack "$PACK" --profile workbench --out "$OUT"
python3 "$BUNDLE/r16.py" verify-assembly --path "$OUT"
# One final operator-authorized qualification only when ready:
bash "$BUNDLE/qualify-r16.sh" "$OUT"
```

The optional `--native-route` installs only the existing R15 loopback/token/Podman-gated endpoint; it remains disabled during qualification. It is not a grading authority. Use the SAME `--native-route` flag for later updates.

## Candidate for a newer upstream

```bash
NEW="$HOME/Downloads/learnharness-r163-updated"
python3 "$BUNDLE/r16.py" plan-update \
  --current "$OUT" \
  --upstream "$UPSTREAM" --upstream-ref NEW_UPSTREAM_SHA \
  --addon-pack "$PACK" --profile workbench --out "$NEW"
cat "$NEW/evidence/update-plan.json"
```

This command does not `git fetch` on its own, download/install dependencies, run npm, deploy, merge or activate a build. `NEW_UPSTREAM_SHA` must already exist locally. The update remains NO_GO pending review and a **single full qualification**. Updated upstream files inside `src/core`, `src/server`, `src/agent`, `src/store`, `electron`, `app/api` or the chat component are reported as high-risk; this heuristic is not a semantic compatibility guarantee.

## Acceptance / known limitations

- Tests: 33 isolated synthetic Git regression cases PASS, including an R15 checkout being renamed away before a portable Workbench + native source-only rebuild, upstream non-overlap refresh, case-sensitive collision, source/overlay tamper, hardlink/symlink rejection, pack identity/profile continuity, build-artifact-aware source integrity and unexpected source injection.
- Can operate offline using Python 3.10+, Git and **local** commits. Real upstream 0.4.1 assembly has NOT executed in this isolated environment, because the full source objects are not available here. The GitHub connector verified the named current refs and selected path non-collisions earlier, but that does NOT constitute a compiled or runtime PASS.
- Stable add-on package namespacing is not yet complete: some R15-added files remain under their existing `components/`, `src/features/gusek/`, and `pilots/operations-research/` paths in the disposable app. This enables cheap upstream updates for now but could eventually collide. The assembler fails closed instead of attempting to rewrite upstream.
- Chat session/knowledge graph, original PDF upstream changes and user data are never modified by the portable layer. Standalone GUSEK chat linking remains intentionally disabled. Native GLPK runtime is never started here.
- No automatic release, production authority, or true browser/GLPK runtime qualification is asserted. The future integration still needs an operator-approved Fedora one-shot run and an independent, fresh-context code review.

## Falsification focus for the next meaningful work

After the real clean 0.4.1 Workbench app passes once, the next highest-value migration is replacing the temporary R15-in-place file paths with fully namespaced add-on imports, using a narrowly defined bridge rather than a custom runtime extension platform. Avoid adopting new upstream private store/agent APIs. If the official LearnHarness later exposes a stable extension API, adapt to that rather than maintaining a parallel plugin manager.
